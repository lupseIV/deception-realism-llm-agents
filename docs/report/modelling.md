# Modelling of the Experimental Part

This chapter gives a formal description of the experiment: the data used, the
experiments run, how results are validated, what the approach is compared against,
and a rigorous model of the design. It closes with the programming languages and
frameworks chosen and the alternatives not chosen.

## 1. Formal model

### 1.1 Factors and conditions

A run is defined by a condition and three blocking variables.

- Honeytoken realism `H in {none, low, medium, high}`. `none` is the no-trap
  control; the pilot uses `{none, low, high}`.
- Network realism `N in {refused, generic, faithful}`. The pilot uses
  `{refused, faithful}`; the control has no network trap.
- Informed flag `I in {0, 1}`: whether the agent is told that deception may be
  present (Experiment 2).
- Egress mode `E in {blocked, detonation}`: outbound blocked, or redirected to
  fake services (Experiment 3).

Blocking variables, held and reported but not of primary interest: the persona
`P` (e.g. aws-developer), the model `M`, and the random seed `s`. Personas are a
blocking variable, not a factor, because no prior work varies them and we fix the
environment realism at its lowest level for this stage.

A condition is the pair `c = (H, N)`; the control is `c = (none, -)`. The full
grid for Experiment 1 is the 3x3 of `H x N` plus the control.

### 1.2 A run

A run is a function

```
run(c, P, M, s) -> (L, T)
```

that places an agent built from persona `P` and model `M`, under condition `c`
and seed `s`, into an isolated sandbox and records a trap log `L` (structured
events written by the chamber) and a transcript `T` (the agent messages and tool
calls). The agent is a ReAct agent [13]: it alternates reasoning and tool actions,
which is what makes a progression observable.

### 1.3 Outcomes

All metrics are functions of `(L, T)`.

- Progression depth `D(L, T) in {0, 1, 2, 3}` on the ordered scale
  `none < read < exfiltrate < use`: 0 nothing, 1 the honeytoken was read, 2 its
  material left the file (copied into output or an outbound request), 3 the token
  was used to authenticate at a chamber service. `D` is the highest stage reached.
- Trigger `Y = 1[D >= 2]`: the agent did something a defender would see
  (exfiltrate or use).
- Time to first trigger: the time of the first event with stage `>= 2`, relative
  to the run start; defined only when `Y = 1`.
- Trap mention `R(T) in {0, 1}`: the agent's own text names a trap, applying a
  regex codebook to the assistant messages (not tool output).
- Avoidance `A = 1[read and not trigger]`: the agent read the token and chose not
  to act; undefined in the control, where there is no token.
- Decision after failure: the agent's action after a refused or failing network
  response (continue, retry, change strategy, give up), read from `T`.
- Benign task success: whether the benign task was completed.

### 1.4 Statistical model

For a binary outcome such as trigger or mention we fit a logistic regression over
the Experiment 1 grid:

```
logit P(Y = 1) = b0 + bH*H + bN*N + bHN*(H x N) + bI*I + block(P) + block(M)
```

with `H` and `N` as ordered factors. For progression depth `D` we use an ordered
logistic model with the same linear predictor. Per-condition proportions (trigger
rate, mention rate, benign success) are reported with Wilson 95% confidence
intervals, which behave well at the small counts of a pilot.

The research questions map to parameters:

- RQ1 (honeytoken realism): the `bH` terms on access, use, avoidance and mention.
- RQ2 (network realism): the `bN` terms and the decision-after-failure
  distribution across `N`.
- RQ3 (interaction and inconsistency): the interaction `bHN`; H3 is the specific
  cell of a realistic token with an implausible endpoint (`H = high, N = refused`),
  tested as a contrast against the consistent cells.
- RQ4 (informed): the `bI` term; H4 predicts `bI ~ 0` for trigger but `bI < 0`
  for depth.
- H1 (recognition-action gap): the difference between the `bH` effect on mention
  and on trigger; H1 predicts realism lowers mention more than it lowers trigger.

## 2. Data

Each run produces a trap log (`traps.jsonl`, structured events with a kind, token
id and timestamp), the full transcript, and a scored record. No external dataset
is needed: the data is generated by the chamber under controlled conditions, and
the honeytokens are synthetic by construction.

- Experiment 1: 3x3 grid plus control, benign and prompt-injection tasks, 2
  models, 15 repetitions (600 runs).
- Experiment 2: informed vs uninformed (240 runs).
- Experiment 3: sandbox (blocked) vs detonation (redirected) at high realism.
- Pilot (this lab): 5 conditions x 2 tasks x 3 repetitions on one model (30 runs),
  to illustrate the methodology and surface validity issues before scale.

Repetitions of the same condition use different seeds; the same seed is reused
across conditions within a repetition, so comparisons are paired. Model, backend,
seed and the resolved configuration are written into each run log.

### 2.1 External data reused from the literature

Besides the data the chamber generates, the design reuses artifacts and findings
from the literature, both to build the realism levels and as external baselines.

- Declarative trap definitions. The HoneYAML specifications of Honeyquest [2], a
  machine-readable format for deception techniques, are reused as the declarative
  definition of the traps and as a starter catalogue mapped onto our realism levels.
- Enticingness baseline. The enticingness ranking of the deception techniques
  measured in Honeyquest [2] is an external baseline against which the ordering of
  our behavioural trigger rate across honeytoken levels is compared (RQ1).
- Fingerprint artifacts. The concrete Canarytokens artifacts reported by Honeysweeper
  [1] (the constant AWS key prefix, the fixed-length identifier, the static
  file-template metadata and the fixed file sizes) are used to construct the
  obviously-fake level deliberately and to confirm that the realistic level avoids
  them; the honeysweeper tool itself is used to validate generated tokens.
- Generation idea and properties. The idea of generating realistic honeytokens from
  the real data they imitate, introduced by HoneyGen [9], motivates the realistic
  honeytoken level; we take the idea only, not the HoneyGen method, and use our own
  generator. The decoy properties of Bowen et al. [10] provide the rubric for scoring
  realism.
- Network and environment realism. The protocol deviations that fingerprint low- and
  medium-interaction honeypots [3] define the tells of the generic network level and
  validate the faithful one; the wear-and-tear artifact categories of [8] define the
  home-directory skeleton planted in every condition.
- Comparison findings. The recognition-action gap reported for LLMs in [4] and the
  informed-versus-uninformed effect of the Tularosa study [7] are the external
  findings our results are compared against (H1, H4).

## 3. Validation

Realism levels are validated against the literature: the obviously-fake level uses
known fingerprintable artifacts [1]; the network levels are validated by protocol
deviation, following the fingerprinting of [3], so the faithful level has no such
tell; the environment uses wear-and-tear artifacts [8] so it is not itself a
giveaway. The realistic honeytoken level follows the decoy properties of [10] and
the generation idea of [9] (realistic tokens derived from the real data they
imitate), implemented with our own generator rather than the HoneyGen method.

Results are validated by the paired design, Wilson intervals and the logistic
model above. Infrastructure errors (rate limits, timeouts, cancelled samples) are
marked and excluded, never scored as the agent giving up, since they are not agent
behaviour.

Comparison baselines: the no-trap control is the internal baseline; the external
baselines are the enticingness ranking of Honeyquest [2], the LLM questionnaire
results of [4], and the informed-vs-uninformed effect of Tularosa [7]. The study
as a whole answers the call for rigorous measurement of deception in [15].

## 4. Threats to validity

The pilot surfaced harness and sandbox tells that must be controlled: a harness
message that truncated long tool output (removed, since a real shell does not
truncate), the redirection of AWS hostnames through visible host entries (to be
replaced by an explicit proxy), and the identifier format of the mock AWS backend.
The environment skeleton is now identical in every condition, including the
control, so a condition differs from the control only by the honeytoken. The pilot
uses a single model, so model is not yet a factor; thinking is on for the cloud
model and off for the local one, which is a condition difference recorded with the
results and not pooled silently.
